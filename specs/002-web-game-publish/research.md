# 研究：公開網頁版敲磚塊遊戲

**功能規格**：[spec.md](./spec.md)

## 研究目標

確認在不改動既有 Python／Pygame 教學檔案的前提下，如何建立一個可在瀏覽器遊玩、可由 Sites 建置並公開發佈的最小版本。

## 決策 1：使用瀏覽器內建 Canvas 2D

**決策**：網頁版以 Canvas 2D 繪製磚塊、底板、球與結果畫面，遊戲狀態以簡單的 TypeScript／JavaScript 物件表示。

**理由**：目前桌面版本是固定 800×600 的即時繪圖遊戲；Canvas 2D 能直接對應矩形、圓形、文字與固定座標，且不需要引入遊戲引擎或後端。這個選擇也能讓 Python／Pygame 與網頁版的概念一一對照。

**替代方案**：

- 直接在瀏覽器執行 Pygame：一般瀏覽器與 Sites 不會直接執行桌面視窗程式，部署與載入風險較高。
- Python-to-WASM：需要額外執行環境與打包流程，超出第一版最小範圍，也不利於清楚示範瀏覽器事件與繪圖。
- 第三方遊戲引擎：可提供更多功能，但會增加依賴、抽象層與教學複雜度；目前需求不需要。

## 決策 2：網站放在獨立的 `web/` 專案

**決策**：在專案根目錄下建立 `web/`，以 Sites starter 初始化；Sites 的 `.openai/hosting.json` 放在 `web/` 內。

**理由**：根目錄目前是 Python／Pygame 課程專案，沒有 `package.json` 或網站入口。獨立子目錄可避免初始化工具覆蓋既有檔案，也使 Sites 的網站專案根目錄、建置輸出與部署 metadata 清楚分離。

**替代方案**：

- 在根目錄初始化網站：容易混淆 Python 與網站依賴，也可能覆寫或污染教學專案結構。
- 另建工作區：會讓 SDD、Python 原始碼與網站規則分散，降低同一功能的追溯性。

## 決策 3：不啟用 D1、R2、Auth 或外部服務

**決策**：網站為不需登入、無持久化的單頁遊戲；回合狀態只保存在目前頁面。

**理由**：規格只要求公開遊玩與單局生命／計分流程，不需要跨裝置恢復、排行榜、檔案或使用者資料。省略 add-on 可降低部署設定與失敗面積。

**替代方案**：若未來要加入排行榜、成績保存或帳號，應另開功能規格，再依需求引入對應的儲存或身份能力，不在本功能預先設計。

## 決策 4：以 60 FPS 為基準的時間更新

**決策**：使用瀏覽器動畫回呼取得經過時間，將球的速度換算為以 60 FPS 為基準的移動量，並限制單次經過時間的最大影響。

**理由**：桌面版本每幀移動固定像素；直接依瀏覽器每次回呼的間隔移動，會在不同螢幕更新率或分頁切換後改變遊戲速度。時間換算可維持既有手感，同時用上限避免單次回呼造成球穿過磚塊。

**替代方案**：固定每次回呼移動固定像素較簡單，但在 60 Hz 以外的環境速度不一致；完整物理引擎則超出需求。

## 決策 5：鍵盤事件由頁面入口集中處理

**決策**：頁面入口集中處理 Space、Left／Right、A／D 與 Escape，讓遊戲模型只接收明確的方向與發球／重置事件。

**理由**：可避免規則函式直接依賴瀏覽器事件物件，並可在入口阻止 Space 捲動、在終止狀態只允許重置。Escape 在瀏覽器中不關閉頁面，需明確記錄為平台差異。

**替代方案**：讓每個遊戲物件自行讀取鍵盤狀態會增加耦合，且難以確保終止畫面完全凍結。

## 決策 6：網站 metadata 與社群預覽

**決策**：網站使用遊戲專屬標題、描述與 Open Graph／X metadata；本版不把額外社群預覽圖片列為必要交付物，保留 Sites starter 的網站圖示即可。

**理由**：網站會公開分享，訪客需要從瀏覽器標題與分享卡辨識內容。預覽圖只做站點級別，不為每一局或每個磚塊產生圖片。

**替代方案**：使用 starter 的通用預覽會讓公開網址難以辨識；若沒有預覽圖，保留標題與描述仍可交付，但新站點應優先補上專屬預覽。

## 結論

以 `web/` 隔離 Sites 專案、用 Canvas 2D 重現既有遊戲、用頁面入口處理鍵盤，以及不配置持久化能力，能在不破壞教學版本的前提下滿足瀏覽器可玩與公開發佈需求。這些決策已納入 `plan.md`、`data-model.md`、`contracts/ui.md` 與 `quickstart.md`。
