# 實作計畫：公開網頁版敲磚塊遊戲

**分支**：`002-web-game-publish` | **日期**：2026-08-28 | **規格**：[spec.md](./spec.md)

**輸入**：來自 `/specs/002-web-game-publish/spec.md` 的功能規格。

## 摘要

本功能在保留既有 Python／Pygame 教學檢查點的前提下，新增一個可在瀏覽器直接遊玩的敲磚塊版本，並以 Sites 公開發佈。網頁版維持 `Day2/prj07_win.py` 的 45 塊磚、生命、計分、碰撞、勝利、Game Over 與 Space 重玩規則；不建立登入、後端、資料保存或其他遊戲系統。

網頁版採用一個單頁、靜態、桌面鍵盤優先的遊戲入口。遊戲邏輯與畫面更新分開，使用固定的 800×600 遊戲座標以維持規則對齊，再以頁面樣式讓遊戲區在桌面視窗中完整可見。Sites 專案放在 `web/`，避免初始化工具改寫根目錄的 Python 教學專案。

## 技術背景

**語言／版本**：既有 Python 3.14.4 與 `pygame==2.6.1` 維持不變；網頁端使用 Sites 產生的 TypeScript／JavaScript 專案與其鎖定的 Node.js 執行環境。

**主要依賴**：`@openai/create-sites@0.2.0` 產生的 Sites 專案、`@openai/sites-vite-plugin` 及瀏覽器內建 Canvas 2D 與鍵盤事件能力；不新增遊戲引擎或外部 API 套件。

**儲存**：不適用；回合狀態只存在目前頁面的記憶體中，重新整理即開始新回合。

**測試**：Sites 專案建置、既有 Python 語法檢查、瀏覽器人工操作驗收；不導入新的測試框架。

**目標平台**：可公開存取的現代桌面瀏覽器，以及 Sites 的 Cloudflare Workers 相容靜態／網站執行環境。

**專案類型**：單頁靜態網頁遊戲與既有教學用桌面遊戲並存。

**效能目標**：遊戲畫面以 60 FPS 為目標；在正常桌面瀏覽器中，球與底板移動不因畫面更新率改變而產生明顯速度差異；終止狀態在下一個可見畫面內顯示。

**限制**：只支援桌面鍵盤；不加入觸控、手把、音效、特效、特殊磚塊、多關卡、排行榜、登入、後端服務、資料保存、自訂網域或第三方遊戲函式庫。既有 `Day1/`、`Day2/` 檔案不可因網頁化而刪除或回溯重構。

**規模／範圍**：一個公開路由、一個 800×600 邏輯遊戲區、一份瀏覽器遊戲狀態模型、一套鍵盤／畫面契約，以及 Sites 建置與公開部署設定。

## 設計決策

- **網站位置**：在 `web/` 建立獨立 Sites 專案；根目錄繼續保存 Python、課程素材與 SDD，避免在非空根目錄重跑初始化工具。
- **瀏覽器渲染**：使用瀏覽器內建 Canvas 2D，保留 800×600 邏輯座標與目前色彩、磚塊排列及物件比例；不加入 Phaser 或其他遊戲引擎。
- **更新時序**：以 `requestAnimationFrame` 驅動畫面，將經過時間換算為以 60 FPS 為基準的更新倍率並限制單次倍率上限，避免切換分頁後球瞬間跳躍；終止狀態不再呼叫遊戲更新。
- **狀態模型**：以單一 `GameState` 管理 `score`、`lives`、`gameOver`、`gameWon`、`bricks`、`paddle` 與 `ball`；`resetGame()` 是勝利與 Game Over 共用的完整重置入口。
- **碰撞規則**：依 `prj07_win.py` 的矩形重疊判定與速度反轉邏輯移植；每一個更新週期最多移除一塊磚並只計分一次，最後一塊磚完成計分後才設定勝利。
- **鍵盤焦點**：遊戲根元素可取得鍵盤焦點；Space、方向鍵與 A／D 的事件在遊戲頁面內阻止瀏覽器預設捲動，終止狀態只接受 Space 重置，Escape 不關閉瀏覽器或改變遊戲狀態。
- **可見介面**：遊戲區使用 Canvas，生命／分數與結果文字同時提供可讀的頁面文字與 ARIA 狀態；`app/layout.tsx` 的頁面 metadata 使用遊戲專屬文案。
- **公開發佈**：Sites 只配置必要的網站專案識別，不配置 D1、R2、Auth 或環境秘密；以建置成功的 `web/` 內容建立版本，人工測試通過後才進行公開部署。

## 研究結論

研究細節記錄於 [research.md](./research.md)，結論如下：

1. Canvas 2D 與瀏覽器動畫迴圈能以最少依賴重現既有 Pygame 的固定遊戲區與碰撞規則。
2. 將 Sites 專案隔離在 `web/` 可同時符合既有教學檔案保留要求與 Sites 初始化流程。
3. 公開遊戲不需要資料庫、檔案上傳、登入或外部整合，因此不啟用 D1、R2、Auth 或其他 add-on。
4. 鍵盤事件與頁面焦點需在介面契約中明確定義，避免 Space 捲動頁面及終止狀態被誤更新。

## 實作階段

1. **準備**：建立 Sites 專案、安裝依賴、確認 `web/.openai/hosting.json` 與既有 Python 工作樹未被改寫。
2. **最小可見切片**：先讓公開遊戲頁面顯示專屬標題、狀態列、800×600 遊戲區、45 塊磚、底板與等待發球的球，並通過本機建置。
3. **核心回合**：完成 `GameState`、重置、鍵盤、固定時間更新、牆面／底板／磚塊碰撞、生命與計分。
4. **結果流程**：完成勝利與 Game Over 的互斥狀態、凍結畫面、結果提示與 Space 完整重玩。
5. **介面與品質**：完成桌面視窗縮放、焦點、可讀文字、網站 metadata／分享預覽與既有檔案回歸檢查。
6. **驗證與交付**：執行建置與 `quickstart.md` 的本機人工測試；人工測試通過後執行 Sites 公開部署，並驗證公開網址。

## 介面影響

- 新增瀏覽器遊戲頁面與鍵盤輸入契約；不新增後端 API、資料庫 schema、登入流程或外部服務。
- 新增內部 TypeScript `GameState` 與遊戲規則函式，但不承諾對外的程式 API。
- 新增 `web/.openai/hosting.json` 作為 Sites 專案的部署識別；不在根目錄改變 Python 依賴。
- 網頁版的 Escape 不對應桌面版的關閉視窗行為；瀏覽器頁籤由使用者自行關閉，Escape 不改變回合狀態。

**結構決策**：使用單一 `web/` 靜態網站，不建立 backend、database、shared package 或新的 Python 模組。遊戲規則在 `app/game.ts` 維持清楚的資料與函式邊界，`app/page.tsx` 只負責瀏覽器輸入與繪製，讓網頁版本可被單獨啟動，同時不破壞既有教學檔案。

## 複雜度追蹤

| 項目 | 原因 | 已拒絕的較簡單替代方案 |
|------|------|------------------------|
| `web/` 使用 TypeScript／Canvas 2D | Sites 的瀏覽器執行環境不能直接執行 Pygame；需要一個可公開遊玩的瀏覽器適配層。影響是遊戲規則在兩個執行環境各有一份實作，需以 `prj07_win.py` 與人工驗收維持對齊；回復方式是移除或停用 `web/` 與其 Sites 設定，不影響 `Day1/`、`Day2/` 或 `requirements.txt`。 | 直接部署 Python／Pygame 無法在一般瀏覽器中執行；使用 Python-to-WASM 或完整遊戲引擎會增加載入、依賴與教學複雜度。 |
