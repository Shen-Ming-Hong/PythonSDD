## 使用者情境與測試

### 使用者故事 1：在手機上操作遊戲（優先級：P1）

玩家使用手機或平板開啟公開的敲磚塊網站時，可以以觸控按鈕移動底板，並以觸控按鈕發球或重新開始，不必依賴實體鍵盤。

**為何是此優先級**：行動裝置若無法完成主要遊戲循環，網站對手機使用者就不具備可玩性。

**獨立測試**：在支援觸控的瀏覽器開啟網站，按住左右控制按鈕、放開按鈕，再按「發球」；可觀察到底板移動、停止、球開始運動，遊戲結束後可按「重玩」回到初始狀態。

**驗收情境**：

1. **Given** 遊戲尚未開始，**When** 玩家按下「發球」，**Then** 球開始移動且按鈕仍可操作。
2. **Given** 遊戲正在進行，**When** 玩家按住「向左」或「向右」後放開，**Then** 底板向對應方向移動，放開後不會持續移動。
3. **Given** 瀏覽器發生觸控取消、視窗失焦或頁面切換，**When** 玩家回到頁面，**Then** 底板不會因殘留輸入而自行移動。
4. **Given** 遊戲顯示勝利或 Game Over，**When** 玩家按下「重玩」，**Then** 磚塊、生命、分數與球的位置恢復初始狀態。

### 使用者故事 2：在不同手機尺寸下完整看見遊戲（優先級：P1）

玩家以窄螢幕、瀏海螢幕或橫向手機開啟網站時，可以看見完整遊戲區與操作控制，不需要水平捲動，文字與按鈕仍然容易辨識與點擊。

**為何是此優先級**：響應式版面是觸控操作可用的前提，也直接影響首次開啟網站時的理解與留存。

**獨立測試**：使用 360px 寬的直向視窗、支援安全區的裝置，以及高度較小的橫向視窗檢查版面；遊戲區維持比例、控制按鈕不超出卡片、頁面不產生水平溢出。

**驗收情境**：

1. **Given** 視窗寬度為 360px，**When** 玩家開啟首頁，**Then** 遊戲卡片、4:3 遊戲畫布與觸控控制可在視窗寬度內排列。
2. **Given** 裝置有瀏海或底部安全區，**When** 玩家開啟首頁，**Then** 主要內容與操作按鈕不被安全區遮住。
3. **Given** 手機切換至高度較小的橫向方向，**When** 玩家繼續遊戲，**Then** 版面縮減上下間距，遊戲與控制仍可使用。
4. **Given** 桌面瀏覽器，**When** 玩家開啟首頁，**Then** 原有鍵盤操作、桌面版面與遊戲規則維持不變。

### 使用者故事 3：維護者可重複驗證並發佈行動版（優先級：P2）

維護者可以依照本專案專用發佈技能，檢查行動版必要條件、執行品質驗證、保存可追蹤的網站版本，並在明確要求公開發佈時使用 Sites 部署。

**為何是此優先級**：可重複的發佈流程能避免只在本機看起來正常，卻把未通過行動版檢查的來源部署到公開網站。

**獨立測試**：在 repo 根目錄執行專案技能驗證，確認技能檔格式正確、流程涵蓋 `web/`、`web/.openai/hosting.json`、行動版檢查、建置與 Sites 版本追蹤；未被明確要求時不執行公開部署。

**驗收情境**：

1. **Given** 網站來源已完成行動版修改，**When** 維護者依技能執行檢查，**Then** 必須先通過 lint、TypeScript 與 production build 才能進入發佈步驟。
2. **Given** `web/.openai/hosting.json` 已有 `project_id`，**When** 維護者執行發佈流程，**Then** 使用既有 Sites 專案，不重新建立或捏造專案識別。
3. **Given** 使用者尚未要求公開發佈，**When** 技能被啟用，**Then** 技能只完成檢查與準備，不覆蓋目前公開網站。

## 邊界情況

- 觸控按鈕需支援 pointer cancel、pointer capture 遺失與視窗失焦，避免左右輸入卡住。
- 玩家在遊戲結束後按住方向按鈕時，不應把終止狀態的殘留輸入帶入下一局。
- `prefers-reduced-motion` 不應影響遊戲必要的畫面更新；本次不額外加入裝飾性動畫。
- 低於 360px 的極窄視窗仍須避免水平溢出；若垂直空間不足，可使用垂直捲動，但不得裁切操作按鈕。
- Sites 設定檔缺少 `project_id` 時，技能必須要求先取得正式專案識別，不得自行產生假值。
- 發佈認證資訊只能以短暫命令環境傳遞，不得寫入 repo、技能檔或文件。

## 功能需求

- **FR-001**：系統 MUST 在觸控裝置或寬度不超過 640px 的版面顯示行動裝置控制區，包含向左、發球／重玩、向右三個可辨識控制。
- **FR-002**：系統 MUST 讓玩家按住左右控制按鈕時移動底板，並在 pointer up、pointer cancel、pointer capture 遺失、視窗失焦或頁面隱藏時清除對應輸入。
- **FR-003**：系統 MUST 保留桌面上的 `Space`、方向鍵與 `A`／`D` 鍵操作，且觸控控制不得改變既有碰撞、生命、計分與勝負規則。
- **FR-004**：系統 MUST 使用裝置寬度 viewport、`viewport-fit=cover` 與安全區間距，並讓遊戲畫布維持 4:3 比例且不造成水平捲動。
- **FR-005**：系統 MUST 在直向窄螢幕與高度較小的橫向版面維持遊戲區、狀態資訊與控制按鈕的可見性；主要觸控目標 MUST 至少為 44px 高或寬。
- **FR-006**：觸控控制與遊戲狀態 MUST 提供可理解的 `aria-label`、狀態播報與鍵盤焦點樣式，且重新開始後 HUD 與畫面同步更新。
- **FR-007**：系統 MUST 在 `.agents/skills/brick-breaker-publish/SKILL.md` 提供本專案專用發佈技能，描述來源檢查、行動版品質閘門、Sites 版本保存、PR 交付與公開部署前提。
- **FR-008**：發佈技能 MUST 重用 `web/.openai/hosting.json` 的既有 `project_id`，不得把 token 或其他秘密寫入檔案；沒有明確公開發佈要求時 MUST 停在驗證與準備階段。

## 關鍵實體

- **遊戲狀態**：目前磚塊、底板、球、生命、分數與勝負狀態；觸控與鍵盤共用此狀態，不新增另一套遊戲規則。
- **輸入狀態**：`left` 與 `right` 兩個布林值；由鍵盤、觸控按鈕、失焦與頁面生命週期事件更新。
- **網站版本**：可由 Sites 儲存與部署的 `web/` 來源快照，須可對應到已驗證的 Git commit。

## 成功標準

### 可量測結果

- **SC-001**：在 360px 寬直向視窗中，首頁水平溢出寬度為 0px，遊戲畫布、狀態與三個控制按鈕均可在頁面內找到。
- **SC-002**：在支援 Pointer Events 的觸控瀏覽器中，按住左右控制至少 1 秒可觀察到底板移動；放開或取消後下一個遊戲更新週期不再因該按鈕輸入移動。
- **SC-003**：觸控「發球」與「重玩」各操作一次，都能在不依賴鍵盤的情況下完成發球及回復初始局面。
- **SC-004**：桌面鍵盤的 `Space`、方向鍵、`A`／`D` 操作與既有人工驗收結果維持通過。
- **SC-005**：`npm run lint`、`./node_modules/.bin/tsc --noEmit` 與 `npm run build` 全部成功，且不新增遊戲執行期外部服務或資料儲存依賴。
- **SC-006**：專案技能通過 `quick_validate.py`，並明確列出行動版檢查、Sites 設定重用、版本追蹤、PR 與公開部署的先決條件。

## 假設

- 目標是現有 Next.js／Sites 靜態網站的行動版增強，不將根目錄 Python 教學程式改造成手機原生 App。
- 遊戲仍以 800×600 內部座標與 4:3 畫布呈現，行動版只調整顯示與輸入介面。
- 現有公開 Sites 專案與 `web/.openai/hosting.json` 可繼續使用；本次未要求立即將新版本公開部署。
- 瀏覽器支援 Pointer Events；不為舊式、無 Pointer Events 的瀏覽器加入另一套複雜輸入抽象層。
- 本專案沒有資料庫、登入、D1、R2 或伺服器 API 需求；發佈技能只處理靜態網站的品質檢查與 Sites 交付。
