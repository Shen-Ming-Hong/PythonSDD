# 任務：敲磚塊勝利流程

**輸入**：本功能的設計文件位於 `/specs/001-add-victory-state/`。

**前置條件**：`plan.md`、`spec.md`、`research.md`、`data-model.md`、`contracts/`、`quickstart.md`。

**測試策略**：規格未要求 TDD 或新增測試框架，因此不建立測試程式；依專案憲章執行語法檢查與實際 Pygame 手動驗收。

**組織方式**：任務依 P1、P2 使用者故事分階段排列；每個故事完成後都能依自己的獨立驗收情境確認結果。

## 任務格式

- `[P]`：可與同階段其他任務平行執行，且不會同時修改相同檔案。
- `[US1]`、`[US2]`：任務所屬的使用者故事。
- 每個任務都指定實際檔案路徑，並依執行順序使用連續的任務編號。

- [X] T002 [P] 建立 `Day2/prj07_win.py` 作為 `prj06` 的新檢查點，保留 `Day2/prj06_lives_restart.py` 不變。

## 階段 2：基礎狀態

**目的**：建立所有使用者故事共用的回合狀態與完整重置流程；本階段完成前不開始個別故事的行為調整。

- [X] T003 在 `Day2/prj07_win.py` 集中建立可重用的完整回合重置流程，初始化 `game_won`，並確保重置會同步還原磚塊、底板、球、生命、分數與終止狀態。

**檢查點**：新檢查點已能保留原本的初始遊戲與重置資料，使用者故事實作可以開始。

## 階段 3：使用者故事 1－完成一局並看見勝利結果（優先級：P1）🎯 最小可行版本

**目標**：玩家擊破最後一塊磚後，能看見勝利畫面、保留當局結果，並用 Space 開始全新回合。

**獨立驗收**：依 `specs/001-add-victory-state/quickstart.md` 清除全部 45 塊磚，確認勝利畫面在最後一塊磚消失後出現；等待並操作方向鍵確認畫面凍結，再按 Space 確認完整重置。

### 使用者故事 1 實作任務

- [X] T004 [US1] 在 `Day2/prj07_win.py` 新增清除版面判定，讓最後一塊磚被擊破並完成 10 分計分後立即進入勝利狀態，且不改變既有碰撞規則。
- [X] T005 [US1] 在 `Day2/prj07_win.py` 讓勝利狀態停止球、底板、磚塊與碰撞更新，繪製 `You Win` 與 `Press SPACE to restart`，並讓勝利畫面的 Space 呼叫共用重置流程。
- [X] T006 [US1] 依 `specs/001-add-victory-state/quickstart.md` 完成 SC-001、SC-002、SC-003 的手動驗收：各自執行 3 次完整清板、3 次勝利凍結與 3 次勝利重玩；確認提示在 1 秒內出現、凍結觀察持續 10 秒，以及每次 Space 都完整重置。
- [X] T007 [US1] 依 `specs/001-add-victory-state/quickstart.md` 完成 SC-005 的理解度驗收：邀請 5 位第一次接觸本版本的玩家各自觀看勝利畫面，確認至少 4 位能只根據畫面文字指出已勝利並找出 Space 重玩方式。

**檢查點**：使用者故事 1 可獨立展示，完整清板後會停在勝利畫面並能重玩。

## 階段 4：使用者故事 2－保持原有的失敗與重玩流程（優先級：P2）

**目標**：新增勝利狀態後，玩家仍能在生命耗盡且尚有磚塊時看到 Game Over 並重新開始。

**獨立驗收**：在 `Day2/prj07_win.py` 中未清除全部磚塊前故意失去三個生命，確認顯示 Game Over 而非勝利；再按 Space 確認回合完整重置。

### 使用者故事 2 實作任務

- [X] T008 [US2] 在 `Day2/prj07_win.py` 檢查並調整生命耗盡分支，確保尚有磚塊時只進入 Game Over、`game_won` 與 `game_over` 不會同時成立，且 Game Over 使用同一個完整重置流程。
- [X] T009 [US2] 依 `specs/001-add-victory-state/quickstart.md` 完成 SC-004 的手動回歸：執行 3 次彼此獨立的失敗測試，每次在尚有磚塊時耗盡三次生命、確認顯示 Game Over 而非勝利，再按 Space 確認每次都完整重置。

**檢查點**：使用者故事 1 與使用者故事 2 都能獨立驗收，勝利與失敗結果互不誤判。

## 依賴與執行順序

### 階段依賴

- 階段 1 可立即開始；T001 與 T002 可平行執行。
- 階段 2 的 T003 依賴 T002 完成，並阻擋所有使用者故事。
- 階段 3 的 T004→T005→T006→T007 依序完成，先交付最小可行版本，再完成第一次玩家理解度驗收。
- 階段 4 依賴 T005，因為要在勝利狀態共用的終止更新閘門上確認 Game Over；T008→T009 依序完成。
- 階段 5 依賴兩個使用者故事的實作與手動驗收完成；T010 可在程式檔案建立後與 T009 平行，T011 最後執行。

### 使用者故事依賴

- **使用者故事 1（P1）**：依賴階段 2；不依賴其他使用者故事，是最小可行版本。
- **使用者故事 2（P2）**：依賴階段 2，並需在使用者故事 1 的終止狀態邏輯完成後進行同檔案回歸調整；不增加新的外部依賴。

### 平行執行機會

- **準備階段**：T001 只讀取基準版本與依賴，T002 建立新檢查點，可平行執行。
- **使用者故事 1**：T004、T005 都修改 `Day2/prj07_win.py`，不可平行；T006 必須等待兩者完成，T007 必須等待 T006 的功能結果。
- **使用者故事 2**：T008 修改 `Day2/prj07_win.py`，T009 必須等待 T008 完成，不可平行。
- **收尾階段**：T010 是獨立的語法與依賴檢查，可與不修改檔案的 T009 平行；T011 統一確認全部結果。

## 實作策略

### 最小可行版本優先

1. 完成階段 1 與階段 2，保留 `prj06` 並建立可執行的 `prj07_win.py`。
2. 完成使用者故事 1，先驗收最後磚塊、勝利凍結與勝利重玩，並完成 SC-001、SC-002、SC-003。
3. 最小可行版本通過後，再完成使用者故事 2 的 Game Over 回歸與 SC-004。
4. 執行 SC-005 的第一次玩家理解度測試，再執行收尾階段的語法與完整快速驗收。

### 增量交付

1. 先交付只有勝利狀態的單一可觀察檢查點。
2. 在不改變勝利規則的前提下確認原有 Game Over 流程。
3. 每個檢查點都可停止、啟動並手動驗收，不加入獎勵分數、音效、特效、特殊磚塊或多關卡。
