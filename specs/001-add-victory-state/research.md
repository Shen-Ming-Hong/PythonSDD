# 研究：敲磚塊勝利流程

**功能規格**：[spec.md](./spec.md)
**日期**：2026-08-26

## 研究範圍

本功能不需要外部服務、第三方整合或新的套件。技術環境、遊戲迴圈順序與檢查點形式都能從目前專案直接確認，因此沒有待澄清項目。以下研究聚焦於如何在既有教學脈絡中加入最小且可驗收的勝利流程。

## 決策

### 1. 以新檢查點保存勝利流程

- **決策**：以 `Day2/prj06_lives_restart.py` 為起點建立 `Day2/prj07_win.py`，不修改 `prj06`，也不抽出共用模組。
- **理由**：憲章要求新功能成為可執行的小型檢查點，並保留舊範例獨立執行。現有專案已使用連續檔案呈現功能進展；單檔複製雖有少量重複，卻最符合學生閱讀與比較前後差異的需求。
- **考慮過的替代方案**：直接修改 `prj06` 會失去前一個教學基準；抽出共用模組會增加尚未需要的模組邊界與匯入概念。

### 2. 使用獨立的勝利布林狀態

- **決策**：保留 `game_over`，新增與它並列的 `game_won`；只有兩者皆為 false 時才更新遊戲。
- **理由**：兩個互斥的終止結果可以直接對應目前已學過的布林值、條件判斷與主迴圈控制，容易在畫面與驗收步驟中觀察。
- **考慮過的替代方案**：用字串或列舉統一所有遊戲狀態，雖可集中管理狀態，但會引入目前功能不需要的新抽象概念。

### 3. 在最後一次磚塊碰撞後判定勝利

- **決策**：維持目前「球更新→生命判定→碰撞處理→計分」的流程；只有成功擊破磚塊並加分後，才檢查版面是否已沒有存活磚塊。
- **理由**：這能讓勝利緊接在最後一塊磚消失後出現，且不會把球落出畫面或其他既有規則改寫成勝利。
- **考慮過的替代方案**：在每幀更新開始時先檢查剩餘磚塊，會讓判定位置不直覺，也可能把版面初始化或其他非碰撞情況誤當成完成。

### 4. 終止狀態使用同一種重玩模式

- **決策**：勝利畫面與 Game Over 都保留結果，停止遊戲更新，並由 Space 執行完整重置；方向鍵或其他按鍵不改變終止中的回合。
- **理由**：延續玩家已熟悉的 Game Over 互動，減少新規則，並直接滿足清楚顯示結果與重新開始的需求。
- **考慮過的替代方案**：自動重開或自動進入下一關會增加計時、關卡或節奏設計，超出本次單一勝利流程的範圍。

### 5. 保持現有技術與手動驗收方式

- **決策**：使用目前的 Python 3.14.4、`pygame==2.6.1`、800×600 視窗與 60 FPS 迴圈；以語法檢查加實際 Pygame 操作驗證。
- **理由**：專案憲章要求以既有 Python／Pygame 為主，且可觀察的遊戲行為不能只靠語法檢查判定完成。
- **考慮過的替代方案**：新增測試框架、音效套件或持久化儲存沒有被本功能需要，會增加依賴與教學負擔。
