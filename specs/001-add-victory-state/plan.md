# 實作計畫：敲磚塊勝利流程

**分支**：`001-add-victory-state` | **日期**：2026-08-26 | **規格**：[spec.md](./spec.md)

**輸入**：來自 `/specs/001-add-victory-state/spec.md` 的功能規格。

## 摘要

新增一個保留既有教學檢查點的敲磚塊版本，讓玩家清除目前版面上的全部 45 塊磚後進入可辨識的勝利狀態。實作以 `Day2/prj06_lives_restart.py` 為基礎建立 `Day2/prj07_win.py`，不修改上一個檢查點，也不引入新套件。

遊戲回合會增加明確的勝利狀態；最後一塊磚被擊破並完成計分後，遊戲停止更新球、底板與碰撞，畫面保留最後結果並顯示勝利提示。玩家在勝利畫面按 Space 時，所有磚塊、生命、分數、球與底板會重置為新回合。原有的 Game Over 流程維持不變。

## 技術背景

**語言／版本**：Python 3.14.4（專案虛擬環境）

**主要依賴**：`pygame==2.6.1`

**儲存**：不適用。

**測試**：Python 語法檢查，加上實際 Pygame 執行與手動驗收；目前未設定測試框架。

**目標平台**：使用專案虛擬環境的本機桌面環境。

**專案類型**：教學用途的單檔桌面遊戲。

**效能目標**：維持現有 60 FPS 遊戲迴圈；最後一塊磚移除後，在下一個可見畫面內顯示勝利結果。

**限制**：保留 `prj06` 作為可獨立執行的檢查點；維持單檔教學風格；使用簡單且明確的狀態；不新增依賴、資料保存、音效、特效、特殊磚塊或多關卡。

**規模／範圍**：一個新的程式檔案、一個額外的終止遊戲狀態、一個固定的 45 塊磚版面，以及一份鍵盤與畫面互動契約。

## 設計決策

- **檢查點策略**：將目前 `prj06` 的行為複製到 `Day2/prj07_win.py`；不重構既有範例，也不把舊範例抽成共用模組。
- **狀態表示**：保留 `game_over` 並新增並列的 `game_won` 布林值。只有兩個終止旗標皆為 false 時才更新遊戲，讓學習者能直接觀察狀態控制。
- **勝利判定順序**：維持目前的更新順序。若球遺失，先依既有規則處理生命；否則處理至多一次磚塊碰撞、加入分數，再檢查是否已沒有磚塊。如此可在最後一塊磚移除後立即轉換狀態，且不改變碰撞行為。
- **重置行為**：使用一個具名的完整重置流程建立初始狀態，讓勝利重玩與既有 Game Over 重玩不會產生不同結果。
- **使用者介面契約**：保留既有抬頭資訊與結果畫面樣式，新增 `You Win` 與 `Press SPACE to restart`；不新增外部 API 或資料保存契約。

## 實作順序

1. 從 `prj06` 建立新的檢查點，保持原始檔案不變。
2. 新增明確的勝利狀態與具名的完整重置流程，涵蓋版面、底板、球、生命、分數與終止旗標。
3. 在磚塊碰撞成功並完成計分後，辨識清板條件；當任一終止狀態成立時，停止移動與碰撞更新。
4. 使用與 Game Over 相同的結果畫面配置繪製勝利訊息，同時保留既有抬頭資訊與 Game Over 分支。
5. 執行語法檢查與 `quickstart.md` 中的情境，包括未修改檢查點的失敗／重玩流程。

## 介面影響

- 不新增公開 Python API、網路端點、檔案格式或外部服務。
- 使用者可操作的鍵盤契約新增一項終止狀態行為：在勝利畫面按 Space 重新開始。
- 內部遊戲回合狀態新增 `game_won`；其他既有狀態與計分規則維持相容。
