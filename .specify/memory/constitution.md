# PythonSDD 專案憲章

## 核心原則

### I. 逐步可執行的學習節奏

每個新功能 MUST 拆成一個可以在本機執行、可以看見結果的小型
checkpoint。實作新功能前 MUST 保留目前已能運作的行為；每個 checkpoint
SHOULD 只引入一至兩個新的 Python 或遊戲開發概念。當功能同時涉及輸入、
遊戲狀態與畫面時，先完成最小可行版本，再逐步加入碰撞、計分、生命等規則。

理由：Day1 與 Day2 已呈現從函式、底板、球、碰撞到生命與重新開始的自然
進階路徑；小步驟能讓每次改動都容易理解、執行與除錯。

### II. 清楚可讀的 Python

程式 MUST 使用描述性名稱、明確的區段與簡單的控制流程。全域設定值
SHOULD 集中在檔案前段；每個函式、方法或類別 MUST 有清楚且單一的主要
責任。教學重點與不直覺的規則 MUST 以繁體中文註解或 docstring 說明。
程式 SHOULD 優先使用目前已熟悉的 `if`、`for`、list、dict 與函式寫法，
避免為了縮短程式而使用難以閱讀的技巧。

理由：目前程式已能以函式、常數、迴圈與類別表達遊戲邏輯；可讀性比提前
套用進階語法更能支持學習與後續修改。

### III. 物件與遊戲迴圈責任清楚

遊戲物件 MUST 將自己的狀態與相關行為放在同一個清楚的類別中；例如
`Paddle` 負責移動、`Ball` 負責位置與速度、`Brick` 負責存活狀態與繪製。
主迴圈 MUST 維持「接收事件、更新物件、處理碰撞與規則、繪製畫面、更新
顯示」的順序。碰撞、計分、生命與重新開始等狀態變更 MUST 放在有名稱的
函式或方法中，不得藏在單純的繪圖程式裡。

理由：目前程式已使用 `update`、`draw`、`reset` 與碰撞函式分工；固定流程
能讓新增遊戲規則時知道應該修改哪裡。

### IV. 可觀察行為必須驗收

每個功能 MUST 在 spec 或 task 中列出玩家可以操作的步驟與預期結果。完成
後 MUST 實際啟動對應的 Pygame 程式，驗證視窗、鍵盤輸入、物件移動、邊界、
碰撞及畫面更新；涉及生命、分數或重新開始時，也 MUST 驗證狀態是否正確。
純函式或小型規則 SHOULD 以簡單的呼叫、輸出檢查或測試驗證，但在尚未
需要測試框架前，不強制導入複雜的測試工具。只通過語法檢查而未確認遊戲
行為的改動，不視為完成。

理由：這個專案的主要成果是可操作的遊戲畫面；手動驗收能直接對應目前的
學習方式，也能抓到語法檢查無法發現的輸入與狀態問題。

### V. 以學習為中心的最小複雜度

專案 MUST 以 Python 與既有的 Pygame 為主要技術。新增套件 MUST 在 spec
或 plan 說明用途，並同步記錄在 `requirements.txt`。不得為假設中的未來
需求加入框架、設計模式、外部服務或複雜架構；若新概念確實是功能所需，
MUST 先用最小範例說明，再加入主程式。程式仍小且適合教學時，可以保留
單檔結構；只有在檔案已難以閱讀或功能邊界已清楚時，才拆分模組並說明
拆分理由。

理由：目前的範例以單檔 Pygame 程式和單一外部套件完成完整遊戲循環；控制
複雜度能把注意力放在 Python 基礎與遊戲邏輯上。

### VI. SDD 文件繁體中文標準

所有由 SDD 流程建立、更新或審查的文件 MUST 以繁體中文撰寫。這包括
`spec.md`、`plan.md`、`tasks.md`、`research.md`、`data-model.md`、
`quickstart.md`、`contracts/`、checklist 及相關審查紀錄；文件的標題、段落
說明、需求、驗收條件、設計決策與表格文字 MUST 使用繁體中文。程式碼區塊、
程式識別字、命令、檔案路徑、套件名稱、API／協定名稱及必要的引用原文 MAY
保留原文；規範關鍵字 `MUST`、`SHOULD`、`MAY` 亦可保留。若原文內容影響
理解，文件 MUST 以繁體中文補充說明。SDD 文件的
新增與審查 MUST 檢查此語言要求。

理由：統一文件語言能讓主要開發與教學團隊直接閱讀、審查、驗收與維護規格，
並減少需求在不同語言間轉譯時的歧義。

## 教學與技術限制

- 執行環境以 Python 虛擬環境為準；目前外部依賴為 `pygame==2.6.1`。
- `Day1/` 與 `Day2/` 是循序漸進的學習範例。新增 checkpoint MUST 讓舊範例
  仍可獨立啟動，不得為了消除少量重複就一次重構所有舊檔案。
- 遊戲程式 SHOULD 保留目前使用的繁體中文區段標題與學習註解；畫面文字
  可依功能需求使用中文或英文，但操作方式 MUST 清楚可理解。
- 遊戲狀態的改變 MUST 使用明確的布林值、數值或物件屬性表達；邊界與
  無效狀態 SHOULD 以簡單的條件判斷、`max`、`min` 或明確的重設流程保護。

## 開發流程與品質閘門

1. 新功能先使用 `$speckit-specify` 描述玩家、目標、操作方式與可觀察的
   驗收結果，不先直接修改程式。
2. 使用 `$speckit-plan` 說明會使用的 Python 概念、遊戲物件與狀態變化；
   若需要超出目前程度的新概念，必須同時說明學習理由。
3. 使用 `$speckit-tasks` 將計畫拆成可執行的小 checkpoint，並依賴關係排序。
   每個 task SHOULD 能在完成後立即執行與驗收。
4. 使用 `$speckit-implement` 逐項完成 task；每次改動 MUST 先驗證受影響的
   程式，再繼續下一項。
5. 實作完成後使用 `$speckit-converge`，確認程式行為、spec、plan、tasks
   與本憲章一致；未完成的行為 MUST 明確保留在 tasks 中。

## 治理

本憲章是本專案的開發依據。每份 spec、plan、task 與完成檢查 MUST 確認
是否符合本憲章；若學習目標需要例外，必須在相關文件中寫明原因、影響與
回復方式。憲章修改必須說明修改原因、受影響的原則與範例，並在修改後
更新版本與日期。

版本依語意化規則管理：移除或重新定義既有原則的相容性破壞變更使用 MAJOR；
新增原則或重要章節使用 MINOR；澄清文字、修正錯字或不改變規則的細節使用
PATCH。每完成一個重要課程階段或證明已掌握新的程式能力時， SHOULD 重新
檢視憲章是否仍然合適；不得為尚未學會的技術預先加入不必要的強制規範。
